# usbvr — PC side of usb-vr, in Rust

Streams the PC screen to the DJI Goggles 3 (`vr_bridge`) and gets head tracking back.
Replaces [`../pc/vrstream.py`](../pc/vrstream.py) (kept unchanged as a fallback): same wire
protocol ([`../device/proto.h`](../device/proto.h)), same bridge, same stats line, but capture,
conversion and encoding happen in-process with the FFmpeg libraries instead of an `ffmpeg`
subprocess + FLV pipe.

```
 KMS plane / PipeWire / X11 / DXGI ──► convert (VAAPI: scale, letterbox, NV12) ──► encode (NVENC/VAAPI/…)
        stamped at PC vblank               stage A thread                             stage B thread
                                                                                          │ Annex-B AU, pts = capture time
 opentrack UDP ◄── pose ◄──────── usb-vr protocol (adb forward tcp:42420) ◄───────────────┘──► vr_bridge
```

## Build

```sh
sudo apt install libavcodec-dev libavfilter-dev libavformat-dev libavutil-dev libdrm-dev libclang-dev
cd usb-vr/pc2
cargo build --release                       # → target/release/usbvr
cargo build --release --features pipewire   # + PipeWire/portal capture (needs libpipewire-0.3-dev libspa-0.2-dev)
cargo test
```
FFmpeg bindings are generated by bindgen against the installed headers (tested with FFmpeg 9.0.2,
libavcodec 63). Without the `-dev` packages, see [env-local.sh](env-local.sh) (headers unpacked from
the `.deb`s, `FFMPEG_INCLUDE_DIR` / `FFMPEG_LIB_DIR`). Windows: `FFMPEG_INCLUDE_DIR`/`FFMPEG_LIB_DIR`
pointing at a shared FFmpeg dev build (e.g. BtbN "shared" builds), `cargo build --release`.

## Permissions (KMS capture)

KMS capture reads the framebuffer the display controller is scanning out. The kernel only hands
out framebuffer handles (`drmModeGetFB2`) to callers with **CAP_SYS_ADMIN**; opening
`/dev/dri/card0` needs group `video`. Give the capability to an installed copy (a rebuild drops
file capabilities, and a capability binary should not live in a user-writable build dir):

```sh
install -Dm755 target/release/usbvr ~/.local/bin/usbvr
sudo setcap cap_sys_admin+ep ~/.local/bin/usbvr
getcap ~/.local/bin/usbvr          # (from libcap2-bin) → cap_sys_admin=ep
```
No `kmsfix` shim and no `KWIN_DRM_PREFER_COLOR_DEPTH` needed: 10-bit framebuffers
(`AR30`/`AB30`/`XR30`/`XB30`, KWin 6 default) are imported directly (the alpha variants are
relabelled as their X twins, identical layout). fp16 (`AB48`, HDR on) is not supported.
`usbvr` drops the capability immediately for every non-KMS run and refuses `--vf` while it holds
it (filters can load plugin code). `--source pipewire` needs no privileges at all.

## Usage

```sh
usbvr --list                                    # outputs, planes, framebuffer formats
usbvr --deploy                                  # push + start vr_bridge, capture the first screen
usbvr --deploy --output eDP-1 --encoder nvenc --bitrate 30M
usbvr --deploy --bridge-args=-M                 # bridge display-timing metrics in its log
usbvr --no-video --print-pose                   # head tracking only
usbvr --source pipewire --restore-token ~/.config/usbvr.token   # Wayland portal, no root (feature)
usbvr --source test --preview                   # test pattern + local ffplay preview
usbvr --source file --input clip.mkv
# PC-only protocol test against the host build of the bridge:
usb-vr/device/build.sh host && USBVR_TMP=/tmp usb-vr/out/vr_bridge_host -N -H -1 -l - &
usbvr --source test --no-forward
```
Stdin: `r` recenter, `i` force an IDR, `q` quit. Ctrl-C quits cleanly (twice: hard).
`--dump out.h264` also writes the exact Annex-B stream; `--no-connect --duration 10` encodes
without a bridge (benchmarks). `--stats-interval`, `--frames N`, `--ffmpeg-log info`.

Stats every 3 s, same fields as vrstream.py, plus PC-side numbers:
```
sent 100.3 fps 30.1 Mbit/s | shown 100.3 fps | capture→shown p50 7.5 ms p95 8.1 ms (capture→send 7.5) |
decode … convert … | queue≤0 dropped 0 | pose … Hz | rtt 0.1 ms | pc: cap 99.9 fps, conv 3.6 enc 3.8 ms, cap→send p95 8.1, skip 0 idr 0
```
`capture` is the PC display's vblank at which the frame was on screen (KMS), buffer arrival
(PipeWire), DXGI present time, or generation time (test/file) — known in-process, no `--capture-ts`
hack. `conv` = capture → encoder input, `enc` = encoder in → AU out, `skip` = frames dropped
because stage B was still busy (never queued), `idr` = forced IDRs.

## Design

Crates (`crates/`), so a UI can be put on top of the library:

| crate | contents |
|---|---|
| `usbvr-link` | protocol, TCP link (writev, no AU copy), receive thread, windowed min-RTT clock sync, IDR requests, opentrack, stats, adb deploy/forward. No FFmpeg. |
| `usbvr-capture` | `Capture` trait + backends: `kms` (libdrm, vblank pacing), `x11` (XShm), `portal` (PipeWire, feature), `dxgi` (Windows), `pacer` (refresh decimation). No FFmpeg. |
| `usbvr-av` | bindgen FFmpeg bindings, DMA-BUF/CPU → AVFrame wrapping (no copy), GPU converter (libavfilter), encoder presets, Annex-B, test/file sources |
| `usbvr` | `session::run(Config, Control, Events)` (library API) + the CLI |

Latency measures:
- **Refresh-synchronised capture.** KMS: `drmWaitVBlank` on the plane's CRTC, then the plane's
  current framebuffer is exported; a frame is only taken when the framebuffer changed (page flip)
  — or when an IDR is needed — and decimated evenly to `--fps` (120 Hz panel → 100 fps takes 5 of
  6 vblanks). `--sync poll` checks the plane every 1 ms and takes a new framebuffer as soon as the
  compositor commits it; `--sync timer` free-runs like ffmpeg's grabbers. PipeWire: buffer arrival.
  DXGI: AcquireNextFrame (DWM present).
- **Zero-copy GPU path.** DMA-BUF → `hwmap` into VAAPI → `scale_vaapi` (hq, aspect kept) →
  NV12 BT.709 limited → `h264_vaapi` directly. For NVENC/x264/AMF/QSV the scaled NV12 picture
  (one VPP pass) is mapped and copied with streaming loads into pooled buffers whose black bars
  were filled once — letterboxing costs no extra pass. Bars are never added on NV12 by the GPU
  (`pad_vaapi` on NV12 writes green); the VAAPI-encoder path pads in RGB.
- **Correct frame rate to rate control**: time_base 1/fps, framerate fps, pts from capture time,
  CBR with VBV = `--vbv-frames` frames. Measured: exactly the requested bitrate (30.0 Mbit/s).
- **No queues.** Stage A (capture + convert) hands frames to stage B (encode + send) through a
  one-frame slot; a newer frame replaces an unclaimed one (`skip`). The AU is written to the
  socket as soon as the encoder returns it.
- **Immediate IDR**: on (re)connect, when the bridge logs a queue overflow / "waiting for next
  keyframe", when frames are sent but none is reported shown for 200 ms (bridge silently waiting
  for a keyframe), on `i`. Encoders get `forced-idr`. vrstream.py waited for the next GOP (2 s:
  199 frames lost at start in TESTLOG #52).
- **Slices as they come:** not possible through libavcodec (no encoder delivers partial AUs), and
  the bridge decodes whole AUs. Would need the NVENC SDK directly (`enableSubFrameWrite`) plus a
  bridge change; not done.

Defaults (TESTLOG #48–53): H.264 High + CABAC, GOP 2 s, CBR, VBV 4 frames, 4 slices, no B-frames;
NVENC `p1`/`ull`/zerolatency, VAAPI `async_depth=1`, x264 `superfast`/`zerolatency` (CABAC; the
hardware decoder doesn't need baseline any more), letterboxed 1920x1080.

## Measured (PC only, 2026-11-20)

KMS path through `--kms-simulate` (hidden test aid: real vblank pacing of the eDP plane
2560x1600 @ 120 Hz, but content from 10-bit VAAPI surfaces exported as DMA-BUF, because this
session has no CAP_SYS_ADMIN — everything except the GetFB2/PRIME export ioctls), host bridge
`-N`, 100 fps, 30 Mbit/s:

| path | capture→send p50 / p95 | notes |
|---|---|---|
| vrstream.py, kmsgrab (`ffmpeg-kms`) → nvenc, `--capture-ts` | 12.1–12.4 ms / 13.3–14.8 | rate control starved to 0.1 Mbit/s by `--capture-ts` (so encode was cheap); capture time = grab, not vblank |
| vrstream.py, kmsgrab → vaapi, `--capture-ts` | 10.8–11.0 / 11.7 | same |
| **usbvr kms → nvenc** | **7.5 / 8.1–8.3** | conv 3.6 + enc 3.8 ms, real 30.0 Mbit/s, measured from vblank |
| **usbvr kms → vaapi** | **7.2–9.7 / 7.8–10.7** | GPU shared with the desktop; varies with load |
| usbvr kms → nvenc before pooled letterbox (3 VPP passes + hwdownload) | 9.6 / 10.8 | single-stage: only 60 fps (each frame > 1 refresh) |

So ~4–5 ms less from capture to the socket than the ffmpeg path, while sending the real bitrate,
and the timestamp starts earlier (at the PC's vblank). Test source (yuv420p 1080p → swscale NV12 → nvenc):
6.9 ms p50 / 8.3 p95. X11 (XShm) works but is slow for an 8192x1760 XWayland root (40 ms; use `--region`;
on KDE Wayland it's black anyway).

IDR recovery against a fake bridge: overflow log → IDR 22 ms later; silent stall → IDR after
~220 ms.

| Preview, dump, deploy/forward | preview/deploy untested here (no display test / no goggles) |

Proposed protocol addition (optional, backward compatible, not implemented on the bridge):
`VR_KEYREQ = 0x86` goggles→PC, sent where `vr_bridge.c` sets `g_need_key = 1` (queue overflow,
`hwdec_submit` failure, swdec error). usbvr already handles it; old PCs ignore unknown types.
Today usbvr infers the same from the bridge's log line and the stall detector.
